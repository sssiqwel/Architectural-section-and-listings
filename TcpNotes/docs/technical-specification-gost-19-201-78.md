# Техническое задание на программу «TcpNotes»

Обозначение документа: `TcpNotes.ТЗ.01`  
Вид документа: техническое задание  
Стандарт оформления: ГОСТ 19.201-78  
Редакция: 1.0  
Дата: 28.09.2026

## 1. Введение

### 1.1. Наименование

Полное наименование: «TcpNotes — клиент-серверная программа обмена заметками по TCP». Краткое наименование: «TcpNotes».

### 1.2. Область применения

Программа предназначена для учебной демонстрации клиент-серверной архитектуры, TCP-соединений, асинхронного ввода-вывода и общего потокобезопасного состояния. Эксплуатация предусмотрена на одном компьютере через интерфейс обратной петли `127.0.0.1`.

## 2. Основания для разработки

Основанием служит учебное задание на разработку приложения «Заметки», состоящего из TCP-сервера и консольного клиента. Документ разработан по ГОСТ 19.201-78 с учётом фактической реализации репозитория TcpNotes.

## 3. Назначение разработки

### 3.1. Функциональное назначение

Программа должна позволять нескольким экземплярам клиента:

1. подключаться к серверу по TCP;
2. добавлять непустые текстовые заметки;
3. получать единый нумерованный список заметок в порядке добавления;
4. завершать клиентский сеанс без остановки сервера.

### 3.2. Эксплуатационное назначение

Программа применяется в локальной учебной среде. Сервер запускается до клиентов и работает до нажатия `Ctrl+C`. Клиент управляется командами из терминала.

## 4. Требования к программе

### 4.1. Требования к функциональным характеристикам

#### 4.1.1. Сервер

Сервер должен:

- прослушивать `127.0.0.1:5000`;
- принимать несколько TCP-подключений без последовательной блокировки приёма;
- читать по одной строке UTF-8;
- обрабатывать `ADD <текст>` без учёта регистра имени команды;
- обрабатывать `LIST` без учёта регистра;
- хранить заметки только в оперативной памяти;
- синхронизировать доступ к общему списку;
- отвечать одной строкой с префиксом `OK`, `NOTES` или `ERROR`;
- освобождать сетевые ресурсы при остановке.

#### 4.1.2. Клиент

Клиент должен:

- подключаться к `127.0.0.1:5000`;
- показывать доступные команды;
- отправлять непустую введённую строку серверу;
- выводить полученный однострочный ответ;
- завершаться по `EXIT` или окончанию стандартного ввода;
- сообщать о недоступности сервера и разрыве соединения.

#### 4.1.3. Протокол

| Запрос | Ограничение | Ответ |
|---|---|---|
| `ADD <текст>` | После удаления внешних пробелов текст должен быть непустым и не содержать `\r` или `\n` | `OK Заметка добавлена. Всего заметок: N.` |
| `LIST` | Дополнительные аргументы не допускаются | `NOTES (список пуст)` либо нумерованный список через ` | ` |
| Иная строка | — | `ERROR Неизвестная команда. Используйте: ADD <текст> или LIST.` |

Максимальный размер строки отдельно не ограничен реализацией и зависит от доступной памяти. Символ перевода строки является границей сообщения. Публичный клиентский API отклоняет встроенные `\r` и `\n`, чтобы один вызов не мог сформировать несколько команд и рассинхронизировать ответы.

### 4.2. Требования к надёжности

- Ошибка ввода пользователя не должна аварийно завершать сервер.
- Отключение одного клиента не должно препятствовать работе остальных.
- Доступ к списку должен оставаться согласованным при конкурентных запросах.
- При отмене сервер должен прекратить приём подключений и завершить активные обработчики.
- После перезапуска сервера восстановление заметок не требуется.

### 4.3. Условия эксплуатации

- Операционная система: Windows, Linux или macOS с поддержкой .NET 10.
- Режим работы: локальный интерактивный запуск из терминала.
- Специальная квалификация пользователя не требуется; необходимы базовые навыки командной строки.
- Сервер и клиенты должны запускаться от обычной учётной записи.

### 4.4. Требования к составу и параметрам технических средств

- 64-разрядный процессор, поддерживаемый .NET 10;
- не менее 256 Мбайт свободной оперативной памяти;
- не менее 200 Мбайт свободного места для SDK и сборки;
- сетевой стек TCP/IP;
- свободный порт `5000` на интерфейсе обратной петли.

### 4.5. Требования к информационной и программной совместимости

- язык реализации: C#;
- целевая платформа: `.NET 10` (`net10.0`);
- кодировка сетевых данных: UTF-8 без BOM;
- сборка: .NET SDK `10.0.401` или совместимый SDK 10.0;
- внешняя база данных и веб-сервер не используются;
- сетевой формат `ADD`/`LIST` должен сохраняться при изменениях реализации.

### 4.6. Требования к маркировке и упаковке

Электронная поставка должна содержать исходный код, файл решения, документацию и лицензию. Каталоги сборки `bin` и `obj`, временные файлы и конфиденциальные данные в поставку не включаются.

### 4.7. Требования к транспортированию и хранению

Исходные файлы хранятся в Git-репозитории или ZIP-архиве. При передаче должны сохраняться имена, кодировка UTF-8 и структура каталогов. Контроль целостности архива выполняется по SHA-256.

### 4.8. Специальные требования

Программа не предназначена для открытой сети: в ней отсутствуют аутентификация, шифрование и долговременное хранение. Для учебного локального применения сервер привязан только к `127.0.0.1`.

## 5. Требования к программной документации

Комплект должен включать:

1. корневой `README.md` с установкой, запуском и использованием;
2. настоящее техническое задание;
3. руководство оператора по ГОСТ 19.505-79;
4. диаграммы классов и последовательности в форматах `.drawio` и `.png`;
5. XML-документацию публичного API рядом с DLL после сборки;
6. файл лицензии.

## 6. Технико-экономические показатели

Разработка не требует платных серверов, СУБД или библиотек. Используются .NET SDK и стандартные сетевые классы. Эффект состоит в наглядной демонстрации TCP-протокола и сокращении объёма инфраструктуры учебного примера.

## 8. Порядок контроля и приёмки

### 8.1. Виды испытаний

- чистое восстановление пакетов;
- сборка Release без предупреждений и ошибок;
- запуск автоматических проверок;
- запуск сервера и двух экземпляров клиента;
- добавление заметки каждым клиентом;
- получение обоих текстов командой `LIST`;
- проверка ошибок для пустой и неизвестной команд;
- проверка наличия XML-файлов рядом с DLL;
- проверка открытия DOCX, PNG и исходников diagrams.net;
- проверка ссылок README и состава ZIP.

### 8.2. Критерии приёмки

Программа принимается, если:

1. `dotnet restore`, `dotnet build` и `dotnet test` завершаются успешно;
2. все автоматические проверки пройдены;
3. два клиента видят общий список в правильном порядке;
4. остановка клиента не останавливает сервер;
5. документация соответствует фактическим командам, типам и структуре;
6. поставка не содержит каталогов сборки, временных файлов и конфиденциальных данных.
